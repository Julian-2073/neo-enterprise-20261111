# NEO 后端开发交接：接口契约与模拟数据替换清单

> 版本：2026-09-30 · 对应桌面 `Neo开发文件2026/growthos-dashboard`。本文是**待共同确认的目标契约**，不是已实现接口的说明。当前 COCA健身只是前端演示企业名称；经营、市场、预测及行动结果均不能据此认定为真实客户数据。

## 1. 当前可运行状态与交接边界

- 主页面：`/` 今日经营、`/analysis/people` 我的客户、`/analysis/goods` 供应链与库存、`/analysis/market` 渠道与竞品、`/analysis/overview` 生意预测/协同、`/reports/weekly` 本周行动周报。
- NEO 主页面由 `growthos-dashboard/lib/neo-demo-data.json` 提供固定演示快照（`isMock: true`，`asOf: 2026-09-24`）；`growthos-dashboard/lib/neo-demo.ts` 计算部分比例、指数与证据文案。页面在 `components/neo-demo/`。
- 主页面**没有调用后端数据接口**。现有 `app/api/data/route.ts` 是较早的 GrowthOS CSV → D1 事件管道，只有 GET 最新数据集与 POST CSV；不能视为下述 NEO 页面契约。`db/schema.ts` 目前只有 `datasets`、`business_events` 两张表，不含企业、库存、证据、行动、预测记录。
- 对话回复是 `lib/neo-demo.ts#getReply()` 的关键词规则；对话和行动进度保存在浏览器 `localStorage`；今日经营简报每次进入首页都会弹出，不记录已读状态。周报读取同一浏览器的行动状态，不包含真实执行结果。
- `app/neo-v2/**` 是旧场景原型，不在本次 COCA 健身接入范围。不要把其中的酒店模拟数据混入 NEO 主页面。

## 2. 首个后端闭环及优先级

第一阶段只做一条可验收链路：**选定企业和统计范围 → 获取经营快照 → 返回带来源的诊断/证据 → 人工确认行动 → 持久化状态与结果 → 周报重新读取**。其余数据源可以分批接入，但未接入的板块必须返回“待接入/待验证”，不能沿用演示数值伪装成实时值。

| 顺序 | 能力 | 第一阶段可验收结果 |
| --- | --- | --- |
| P0 | 企业身份、权限与数据范围 | 服务端确定 `businessId`，用户只能读取/修改获授权企业的数据；COCA 名称由企业资料返回。 |
| P0 | 经营快照和证据 | 统一返回截至时间、统计口径、值、来源、质量状态；首页与证据抽屉使用同一快照版本。 |
| P0 | 行动草案与状态 | 人工确认后保存到服务端；另一设备查看得到同一状态，记录操作者和时间。 |
| P0 | 周报 | 从已保存行动和指标快照生成，未发生的结果显示“待记录”。 |
| P1 | 商品/库存、渠道/市场接入 | 替换静态商品、渠道支出、市场事件；保留来源和验证状态。 |
| P1 | 情景预测 | 明确模型版本、输入快照、假设、回测状态及人工审核；不得把演示区间称为真实预测。 |
| P2 | 智能体对话 | 另立对话契约和安全边界；当前关键词回复只供演示，不能作为上线 AI 能力。 |

## 3. 通用接口约定（建议）

以下路径是**建议接口**，尚未在代码中创建；前后端确认后再固化为 OpenAPI。采用 JSON、UTF-8。由服务端根据已认证用户确定企业访问权限，不信任前端单独传入的 `businessId`。写接口要求认证、授权、请求校验和审计；现有无企业授权的 `GET/POST /api/data` 在接入真实数据或扩大站点访问范围前应禁用或保护；私有演示访问限制不能替代服务端授权。

每个读取响应都带：

```json
{
  "meta": {
    "businessId": "coca-fitness",
    "businessName": "COCA健身",
    "snapshotId": "snap-2026-09-24-r1-douyin",
    "asOf": "2026-09-24T23:59:59+08:00",
    "periodStart": "2026-07-27",
    "periodEnd": "2026-09-20",
    "timezone": "Asia/Shanghai",
    "scope": { "productId": "R1", "channelId": "douyin", "label": "R1 / 抖音店铺 / 近8周" },
    "dataStatus": "demo"
  },
  "data": {}
}
```

- `dataStatus` 建议固定枚举：`demo | verified | partial | pending | stale`。字段级也可使用该状态，因为同一页面可能混有真实内部数据与待验证外部消息。**缺数据返回 `null` + 状态及原因，不用 0 代替。**
- 金额在 API 中统一用整数分（`amountCents`），展示层再转元；比例统一用 0–1 小数，附分子、分母和口径。当前演示 JSON 金额单位是元，接入时需要显式换算。
- 时间统一 ISO 8601；自然日和周边界使用 `Asia/Shanghai`。库存“当前时点”和经营“近 8 周”不能暗中合并为一个统计范围。
- 证据引用使用稳定 `evidenceId`，并携带 `sourceType`、`sourceName`、`sourceRecordId`/URL（可用时）、`observedAt`、`verifiedAt`、`scope`、`method`、`limitations`。市场事件的“同期”不等于因果。
- 列表支持游标分页；读取请求固定或显式传入 `snapshotId`，避免首页、详情和周报看到不同版本。未确认或冲突的行动更新应返回明确错误，不静默覆盖。

## 4. 建议资源与字段契约

| 建议接口 | 页面/用途 | 最小返回或请求字段 | 当前来源与注意点 |
| --- | --- | --- | --- |
| `GET /api/v1/businesses/current` | 全局顶部、简报身份 | `businessId, businessName, authorizedScopes` | 目前只有 `meta.business=COCA健身`；不要据此创建真实客户记录。 |
| `GET /api/v1/operating-snapshot?scope=...` | 今日经营、我的客户、供应链、渠道 | 通用 `meta`；`issue{id,title,status,evidenceIds}`；`conversion`、`financial`、`inventory`、`market` 分区，未接入分区可为空 | 可先做单企业单快照；所有卡片必须保持范围一致。 |
| `GET /api/v1/briefings/today?date=YYYY-MM-DD` | 每次进入首页的今日简报 | `headline, judgment, policy[], enterprise, marketEvents[], opportunities[], generatedAt, snapshotId`；每项带来源/验证状态 | 行业政策目前没有真实来源，应为空列表 + `pending`；不能伪造政策。 |
| `GET /api/v1/evidence/{evidenceId}` | 证据抽屉、诊断追溯 | `id,title,value,unit,scope,sourceType,sourceName,sourceRecordId,observedAt,method,limitations,verificationStatus` | 当前 `evidenceRecords` 的文字是拼接出来的演示证据，正式版需引用可复核记录。 |
| `GET /api/v1/forecasts?scope=...&snapshotId=...` | 预测页 | `modelVersion, trainedOrCalibratedAt, backtestStatus, historicalWeeks[], baselineWeeks[], totalRange, intervalMeaning, assumptions[], judgment, evidenceIds` | 目前 4 周曲线和 105–135 是本地预设，不是统计置信区间或已验证增量。 |
| `POST /api/v1/forecasts/scenarios` | 方案比较 | 请求 `snapshotId, baselineId, assumptions{budgetMultiplier,eta,...}`；返回 `scenarioId, projectedWeeks[], totalRange, constraints[], modelVersion` | 当前 A/B/C 是固定情景；不能只接受前端传来的结果数字。 |
| `POST /api/v1/actions` / `GET /api/v1/actions/{id}` | 行动草案 | `issueId, scenarioId?, title, ownerIds[], dueAt, goal, hypothesis, observationMetricIds[], evidenceIds[], status` | 由服务端分配 ID；草案创建不触发采购、投放或通知。 |
| `PATCH /api/v1/actions/{id}/status` | 人工确认、执行、观察、复盘 | 请求 `expectedVersion, nextStatus, note?, outcome?`；返回最新记录及 `actorId, changedAt, version` | 状态流转需服务端校验；记录实际结果，不能把“演示执行”当作已完成任务。 |
| `GET /api/v1/reports/weekly?weekStart=...` | 本周行动周报 | `period, snapshotId, issueSummary, actions[], outcomes[], unresolvedItems[], generatedAt` | 当前周报只有本机草案状态，真实版从服务端读。 |

### 关键分区的字段与计算口径

| 分区 | 需要的数据 | 当前演示口径 / 后端待确认 |
| --- | --- | --- |
| 客户转化 | 每周 `A1/A2/A3/A4`、八周汇总、前一等长周期、商品/渠道范围 | 当前 A3→A4 = `310/2480=12.5%`，前期为预置 15.7%；这只是阶段量比，**不是已去重的同批客户转化率**。真实来源须定义用户/会话去重、退单、跨渠道归因和 A 阶段映射。 |
| 财务 | 净成交额、商品/平台/履约成本、投放费用、贡献毛利 | 当前 `589000 - 348000 - 88000 = 153000` 元；贡献毛利不是净利润。应明确订单口径、退款、税费、成本确认时点。 |
| 库存/供给 | 商品与 SKU、角色、可售、在途、预计到货、库存成本、安全线、每周达标 SKU 数 | 当前 R1 可售 42 件、在途 180 件、目标达标率 80%；库存成本货值是当前时点数据，不能与八周销售额当成同周期量。达标定义及覆盖天数算法尚待业务确认。 |
| 渠道/市场 | 渠道费用、商品角色矩阵、需求信号、市场事件、机会 | 当前“竞品促销”“搜索热度”等是未验证演示观察。正式版要有原始出处、时间、关联范围、审核结果；机会应能追溯信号和证据。 |
| 预测 | 历史每周有效成交、未来周中位/区间、情景假设与约束 | 当前 4 周总区间 105–135 人，周界限不能直接相加为总区间。真实版须给模型版本、回测、适用范围及区间解释。 |
| 行动/周报 | 草案、负责人、计划时间、状态、执行记录、结果指标 | 当前状态顺序是 `draft → human_confirmed → executing_demo → observing_demo → reviewed_demo`；正式版应另定真实状态枚举和审计规则。 |

## 5. 模拟数据替换清单

| 位置 | 当前演示内容 | 替换动作 | 验收点 |
| --- | --- | --- | --- |
| `lib/neo-demo-data.json` / `lib/neo-demo.ts` | COCA 名称、8 周数据、商品、渠道、市场、预测、行动、智能体预设与派生比值 | 把静态数据替换为服务端响应；保留可测试的纯计算函数；为演示模式保留明确隔离的 fixture | 改企业/日期/范围后六个主页面一致更新；无数据不显示旧数。 |
| `components/neo-demo/shell.tsx` | 顶部企业名和“模拟数据” | 读取有权限的企业资料与快照状态 | 不跨企业串数据；身份和来源标签一致。 |
| `components/neo-demo/prototype.tsx` | 首页判断、A1–A4、财务、商品/库存、渠道、协同、预测图与行动；多处 `42/72.2%/12.5%/105–135/09.24` 等写死值 | 按组件接分区数据，清理硬编码值、固定时间轴和固定说明；证据 ID 指向同一快照 | 更换测试快照后标题、图、卡片、证据抽屉和预测均同步；范围、日期、单位正确。 |
| `components/neo-demo/today-briefing.tsx` | 静态判断、政策占位、42 件、市场事件与机会；每次进入首页弹出，不保存已读标记 | 简报改由服务端生成；政策无来源继续显示待接入；每次进入首页仍应弹出 | 当天数据更新或企业切换不会显示另一企业的简报；来源及生成时间可见。 |
| `components/neo-demo/weekly-report.tsx` | 固定一条行动、`12.5%`、`42 件`、`09.24`，状态读本机 | 读取周报接口与真实行动记录，空周报要有明确空态 | 跨设备状态一致；未执行时不出现执行结果。 |
| `lib/neo-demo.ts#evidenceRecords`、`#getReply` 与对话面板 | 文案拼接证据、关键词回复、演示对话存本机 | 证据由服务端记录生成；若暂不做 AI，保留“演示对话”标识或关闭输入 | 回答不得引用不存在/过期证据；每条诊断可追溯。 |
| `app/api/data/route.ts`、`db/schema.ts`、`drizzle/` | 旧 CSV/D1 管道，两张旧表；POST 尚未做用户/企业授权 | 先决定旧接口保留、迁移或隔离；新增领域表与 Drizzle 迁移，检查并应用迁移 | 公网不能匿名写数据；数据隔离、迁移与回滚可验证。 |

替换时还要全局检查静态的“模拟数据”“演示基线”“本机记录”、固定日期/百分比/人数和 `localStorage` key。标签应随真实 `dataStatus` 变化，但部分接入时仍保留待验证标识。

## 6. 后端开始前需要确认的业务问题

1. COCA健身是否只是展示名？谁有权授权使用品牌及真实数据？企业 ID、管理员和可访问成员是谁？
2. 第一批真实来源是什么：订单/退款、广告费、客服线索、商品 SKU、库存/在途、渠道活动、政策/竞品？每项由谁提供脱敏样例和刷新频率？
3. A1–A4 是事件次数、独立用户、会话，还是同一批客户？跨平台 ID 怎样归并？“有效成交”如何处理退单？
4. 净成交额和贡献毛利的财务口径、库存成本估值、安全库存和供给达标规则由谁确认？
5. 预测先做规则情景还是模型预测？真实历史数据量、回测窗口、人工审核责任人是否具备？
6. 行动草案是否仅在站内流转，何时允许通知、创建外部任务或执行投放/采购？第一阶段建议无外部副作用。

## 7. 联调与完成标准

- 后端提供一套**脱敏的同一企业**样例，覆盖正常、缺数据、过期数据、无权限、不同快照、状态冲突六种情况；前端不从演示 JSON 偷拿缺失值。
- 先完成 `经营快照 → 证据 → 人工确认行动 → 另一设备读取 → 周报` 的端到端联调，再扩展市场和预测。
- 指标与证据的范围、截至时间、来源一致；数值计算有单元测试，关键读取/写入有接口测试，主页面有验收用例。
- 无权限不能读取或修改企业数据；写操作记录操作者与版本；不允许匿名 CSV 写入。
- 真实数据上屏前仍要保留演示标识；当字段经业务核实并完成联调，再逐项改为真实状态，不能一次性去掉全部免责声明。
- 发布演示版与接入真实业务是两个里程碑：前者可用私有访问完成，后者以上述数据、权限和闭环验收为准。

## 8. 给后端同事的文件入口

项目根目录是 `growthos-dashboard/`；运行方式和历史能力见 `README.md`。重点先读：`lib/neo-demo-data.json`、`lib/neo-demo.ts`、`components/neo-demo/prototype.tsx`、`components/neo-demo/today-briefing.tsx`、`components/neo-demo/weekly-report.tsx`；再对照旧数据管道 `app/api/data/route.ts`、`db/schema.ts` 和 `drizzle/`。`docs/design-handoff/` 保存原始设计交接资料，其中旧客户称呼属于历史文档，不是当前页面数据源。
