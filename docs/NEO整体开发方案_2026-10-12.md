# NEO 整体开发方案：从经营分析走向持续决策与行动

日期：2026-10-12。状态：开发方案，未执行本方案中的代码改造。

## 1. 产品目标与本次判断

NEO 的目标是：经营者提出目标或遇到问题后，系统持续汇集可信事实、调查关键未知、比较可行选择、记录团队行动，并根据后续结果调整判断。

这次功能突破的主交付是一个持续保存的「经营议题」。客户、库存、渠道、预测和周报成为同一议题的不同视图。老板不用在不同页面重新解释问题，团队能继续补充资料，后续变化可以回到原来的判断与选择。

首个完整场景：**主力商品供给与成交承接出现异常，是否补货、调拨或增加投放？** 同时用「退款与费用异常」验证底座能支持不同类型问题，避免把整个系统写成一套补货规则。

基础事实：项目已有经营导入、快照与经营代次、身份关联、证据查询、专业调查、确定性计算、预测与方案、部分执行登记、实际对照和确认经验。需要接续和收拢，不应重复建设。

## 3. 必须重构的架构

### 3.1 统一经营上下文和版本引用

当前旧快照与新经营代次并存。保留历史读取，将转换集中到入口适配层；当前议题内部统一使用 `OperatingContextRef`：企业、数据性质、经营版本、业务期间、可知时间、配置版本、资料完整性及新鲜度。

预测、方案、判断和执行观察各有不可变引用。旧结果继续可读；数据变化时标记需复核并产生新版本，不静默覆盖。处理旧选择仍然有效、原预测需要更新的情况，不把所有资料更新都解释成行动失效。

### 3.2 按问题规划调查

把“关键词选专业 → 依次写报告”重构为“明确问题 → 读取事实 → 找到关键未知 → 安排调查 → 判断是否足够”。

`TaskPlan` 必须记录任务类型、目标、范围、已有事实、待检验假设、所需证据、工具、步骤依赖和完成条件。前后端共用契约；意图识别由一处负责，另一处只验证和展示。简单事实查询直接计算；意图有歧义时模型辅助规划并验证工具与范围。

独立调查允许并行；需要其他结果的步骤等待依赖。调用失败可以保存部分事实、列出未完成事项；取消、状态未知、幂等和检查点恢复继续有效。保留当前 unlimited 使用策略，完成条件与超时用于执行可靠性，不借改造恢复旧的费用上限。

### 3.3 结构化结论与分层核验

`Assessment` 分为事实、假设、方案与限制。事实带数值、单位、期间与证据引用；假设带支持证据、反证和验证办法；方案带条件、成本、计算引用与停止条件。

精确数值、引用、范围与版本由程序核验；模型重点审查因果解释、外部信息适用性和跨领域推断。核验每条陈述使用相关证据及必要反证，避免每批重复完整目录；保留批量、缓存和恢复能力。

事实通过而解释失败时，用户仍能看到可用事实及解释缺口。禁止把推测发布成事实，也不应因一段解释失败而抹掉正确计算。

### 3.4 统一结果交付与前端状态

统一基于企业/资料/议题的资源缓存与订阅，收拢分散轮询。第一版采用共享轮询、请求去重和结果版本检查；需要推送时再评估事件流，无须为了重构先引入新基础设施。

任务状态、摘要和详情分开读取。无任务时缺失研判不能触发持续高频请求。加载中、数据缺失、无权限、模型调查中、历史结果失效分别展示。

首页进入预测、方案、行动或复盘时携带议题和结果引用；后退、刷新、跨页面保留选择。历史失败折叠并指明后续有效结果。收到迟到回包不改变新企业或新资料的页面。

### 3.5 明确服务职责并逐步迁移

- TypeScript 服务负责企业访问、业务对象、数据与结果持久化、计算/预测接口及页面投影。
- Python 服务负责任务计划、模型/调查工具执行、检查点和执行事件；业务计算通过已有确定性能力完成。
- 执行事件带任务、序号和版本，消费方幂等对账；UI 不以本机状态判断服务器任务已完成。
- 保留 D1/Drizzle、R2、FastAPI、Python 任务与检查点基础。按职责拆分过大的文件，不先微服务化，也不默认添加图数据库或更多模型。
- 每条业务路径迁移后再收缩旧适配器；历史任务恢复必须通过验证后才移除对应旧执行代码。

## 4. 新增和补齐的业务能力

### 4.1 企业数据准备

按经营问题列最小资料清单；设置企业目标、来源、统计规则、商品/渠道/仓库映射和客户身份规则。允许 CSV 起步；展示完整性、最后同步、覆盖期间、拒绝行与缺口影响。补齐资料后能继续原议题。

持续接入先选择真实试点的一种来源，验证重复数据、更正、删除标记、延迟与断线恢复；来源接口授权、字段和同步时效确定后才承诺实时。OpenMetadata 的目录同步不等于订单、库存业务记录同步。

### 4.2 经营议题与主动发现

议题包括目标、问题、范围、状态、负责人、关联事实/调查/方案/选择/行动/复盘和变化记录。状态区分调查中、待补资料、待选择、跟进中、观察中、已复盘、已关闭；关闭须记录原因。

异常候选先通过规则与计算发现，按影响范围、紧迫性、证据充分度和处理成本排序；金额无法可靠估计时保持未知。相同对象、期间和问题合并，持续恶化才重新提醒。用户能确认、搁置、关闭或转为调查议题。

### 4.3 调查与资料补齐

支持自然语言问题与目标。每个资料缺口对应具体记录/字段、影响、补充方式和下一步分支。人工说明必须标记为业务陈述，不能自动升级为已核验事实。

例如零可售：先列出有关库存位置及到货记录；确认已上架后重新计算可售与调拨；确认未上架则跟踪上架；缺批次关联则明确请求关联记录。退款议题需要订单、原因和费用明细，不套库存调查模板。

### 4.4 目标与方案

支持贡献毛利、履约和现金约束下的方案比较；数据支持时解释目标差距与可行性，资料不足时给出最低验证条件。目标值与预算由老板确认，系统不能私自承诺增长目标。

候选包含不同作用机制；可以是保持现状、先验证、补货、调拨、承接或投放。维持同一计算范围和基线，超过供给、现金、时间约束的组合显式拒绝。不足以支持三个可行方案时解释原因，不为凑数造方案。

需求响应区分历史估计、业务假设和未知。展示敏感性、盈亏门槛、所需新增成交、现金占用、较差情景和停止条件；未校准区间不能标成概率保证。延迟到货、退款、取消和缺失成本进入适用约束。

### 4.5 团队反馈与执行观察

负责人可接手事项、补充资料、反馈进展和阻塞；老板确认选择与负责人反馈分开记录。每项行动关联检查事项、期限、指标和凭据。

统一普通方案、AI 候选与补货求解的选择和结果入口。已有执行凭据校验、实际对照与经验确认复用；用可选择的源记录替代手填难查的编号。投入未执行、观察未成熟、执行凭据更正均有明确状态。

第一版在已有成员角色内完成基本分工与站内提醒。跨平台发送、采购和投放写入留在后续集成范围，不把自动执行作为本轮完成条件。

### 4.6 周期复盘与持续改进

周报带入上期未完成事项、原选择、执行量、实际投入、观察结果、偏差及阻塞，不只列本周新保存选择。支持查看过去期间和保存的复盘版本。

复盘对需求响应、交付时间、成本或规则做假设结算。经验包含来源、适用对象/期间、确认人、支持与反证、失效条件；新建议说明引用哪些经验以及为何适用。经验冲突、输入更正或过期后撤回引用。

观察差异不自动归因于行动。具备业务条件时可做小范围对照；自动训练模型不是第一版必要条件。先验证正确记录、合理复用与可解释的建议更新。

## 5. 开发顺序：每个阶段交付可用业务结果

顺序为 S0 → S1 → S2 → S3 → S4 → S5。S6 行业扩展依赖 S4 完整闭环；不要求先做完所有行业才开展真实试点。

| 阶段 | 业务结果 | 重构/开发工作 | 完成门槛 |
|---|---|---|---|
| S0 当前基线与验收样本 | 知道当前哪些路径可用及哪些必须保留 | 在制变更归档、版本指纹、冻结样本和一次任务时间账 | 路径、状态、模型调用与已知失败可回读；不把旧报告当新验证 |
| S1 数据到首个经营议题 | 新企业能导入资料并追踪一个问题 | 统一上下文/结果引用、首次设置、共享页面数据、议题及事实快路径；修复基线承接 | 新企业完成导入→异常→议题→查依据，刷新/跨页不丢失；资料缺口可补齐 |
| S2 调查与判断 | 同一议题得到可靠事实、原因假设和下一步 | 统一任务契约、按需调查、依赖调度、结构化结论、分层核验、异常排序 | 两类议题均可调查；误拒和事实错误分别记录；失败保留可用结果 |
| S3 可行选择 | 老板知道选什么、成立条件及何时停止 | 目标/约束、敏感性与盈亏门槛、同基线方案、统一选择记录 | 明确可行/不可行/资料不足；选择可回读；不把条件收益称为实际收益 |
| S4 执行与复盘 | 团队能跟进，老板下周看到结果 | 接手、进展/阻塞、凭据、实际观察、周报结转、确认经验衔接 | 至少一个模拟完整周期和真实试点的连续观察；未成熟结果保持未知 |
| S5 主动经营与经验更新 | 新变化主动进入已有议题并影响判断 | 持续数据来源、变化触发、去重/静默提醒、经验适用与失效、建议变化解释 | 可解释每次提醒和建议变化；断线/更正能恢复；真实运行连续稳定 |
| S6 行业扩展 | 共用底座支持另一类经营流程 | 酒店流程完善；按实际试点选择高客单、生活服务或连锁 | 每个行业有专用输入、约束、流程、执行与观察验收；不以页面截图代替完成 |

S1 已经提供首次价值，不等待编排整体替换。S2 先迁移一个调查场景，验证后扩大；S3 复用现有计算和求解。每阶段至少一个独立可用交付，阶段验收通过后才扩展下一依赖。

## 6. 核心对象及契约

| 对象 | 必需内容 | 关键约束 |
|---|---|---|
| OperatingContextRef | businessId、dataNature、经营版本、期间、knownAt、配置版本、质量与新鲜度 | 客户/商品/渠道/库存及计算范围可核对；跨企业引用禁止 |
| OperatingIssue | 问题、目标、范围、状态、负责人、关联记录、变化历史 | 同一议题跨页面与跨周期存在；可关闭和重开并记原因 |
| TaskPlan / TaskEvent | taskType、目标、证据需求、工具、依赖、完成条件；事件序号与版本 | 范围冻结、权限检查、重试幂等、终态不可被迟到事件倒退 |
| Assessment | facts、hypotheses、candidates、limitations、验证状态、结果版本 | 每条事实绑定证据；假设带验证条件；部分发布状态明确 |
| Candidate / Decision | 基线、参数、证据、可行性、成本、门槛、停止条件；选择理由与确认 | 同基线才能比较；选择不等于执行；保留保持现状选项 |
| Followup / Execution | 接手、事项、日期、进展、阻塞；实际执行量和来源凭据 | 实际与计划分开；凭据更正需复核；不伪造自动完成 |
| Review / Experience | 原假设、执行、观察成熟度、结果、偏差、适用范围与失效 | 未成熟不出收益结论；无对照不宣称因果；经验可撤回 |

## 7. 验收标准：业务正确、体验可用、运行可靠

以下数字是建议验收门槛，尚未达到验证。先记录 S0 基线，再测同设备、同资料、同模型配置；分别记录服务器处理、排队、工具和模型耗时。模型供应商时延不能混称页面性能。

### 7.1 固定业务样本

冻结 30 个案例并保存期待结论与证据：10 个事实/范围问题、6 个异常调查、6 个方案与约束、4 个执行复盘、4 个资料不足或历史更正场景。每次模型评价至少重复 2 次，并保留失败，不选最好一次。行业扩展追加本行业样本，不借用电商通过率。

- 事实值、单位、期间、去重规则及引用正确率必须 100%；任何关键资金/供给计算错误阻止该路径交付。
- 跨企业、跨数据性质、无权写入、过期回包串范围、重复选择/执行写入：专门案例全部阻断。
- 模型生成结论人工复核至少 90% 满足「回答问题、依据可查、事实/假设分清、下一步可做」。出现未经支持的关键决策事实须修复后复测；误拒、遗漏和幻觉分别统计。
- 已有事实问题不发模型请求；存在解释需要时可在返回事实后继续调查，不用禁止模型来制造速度成绩。

### 7.2 页面与任务体验

- 本地暖态下事实查询端到端 p95 建议不超过 2 秒；议题页首批经营事实建议 3 秒内可见。按固定 30 次测量保存分布，不承诺外网或冷启动相同时延。
- 复杂调查记录首次有用结果和最终完成时间；目标是相对 S0 减少不必要调用和重复证据输入，建议 p95 总耗时下降 30%，同时业务质量不能下降。未满足时说明队列、工具或模型占比并决定下一步，不隐去尾部失败。
- 相同范围共享一个资源刷新调度；无任务无变化时不持续每 2—3 秒重复读取完整工作台。
- 数据加载时不显示成「没有资料」「没有权限」；服务器失败有可操作错误和重试入口。页面完成、任务完成、资料足够为不同状态。
- 逐页验证首页→议题→证据→预测→方案→选择→执行→复盘，返回、刷新和链接重开仍保留正确引用。关联结果不存在时说明缺失，不用另一个版本静默替代。
- 用浏览器性能记录确认可见交互卡顿，保存至少 3 次一致的页面操作；不能只凭轮询代码宣布已解决掉帧。

### 7.3 业务闭环案例

**案例 A：供给与投放。** 导入销量、库存、到货、成本与费用 → 发现零可售 → 核实批次/上架 → 比较保供、调拨或投放 → 保存选择 → 负责人反馈 → 关联到货/费用凭据 → 观察实际 → 复盘假设。预算不足、到货延期、资料缺失和取消选择均须通过。

**案例 B：退款与费用。** 发现同期退款与费用异常 → 查订单和费用明细 → 原因不足保持假设 → 保存核查事项 → 补原因分类 → 更新建议 → 观察后续变化。不能把同期出现解释为因果，也不能因为不做补货就无法进入跟进流程。

**案例 C：恢复与历史。** 调查中断/取消 → 回读可用事实 → 恢复不重复未知模型调用 → 历史凭据更正 → 原结论标记需复核 → 新结论引用新版本；旧判断和老板理由仍可查。

### 7.4 工程验证

- 受影响业务行为有针对性测试；数据库迁移检查、范围/权限/状态恢复检查、类型检查、构建和真实浏览器流程通过。每个独立切片按仓库要求完成全量构建与相关测试；完整发布候选再运行项目全量检查。
- 当前入口命令：`npm run typecheck`、`npm run test:python`、`npm run test:node`、`npm run build`，构建后 `node --test tests/rendered-html.test.mjs`。本地稳定验收使用 `npm run build:local:stable` 与匹配构建运行，核对 source/build fingerprint。
- 真实模型验收单独记录模型/配置、资料版本、调用次数、耗时、结果与人工判断；规则/合成样本通过不替代这项。
- 全部验证保留日志、来源范围、版本、失败和恢复证据。回退是代码/配置/读路径回退，不删除已保存经营记录。

### 7.5 真实企业价值验收

选择 1—2 家同类企业，连续至少 4 个经营周期，先记录现有查数、协调和决策时间。建议邀请老板及实际负责人共同评价，重点覆盖 5 个真实议题；不足 5 个则记录样本不足，不补造。

- 至少 80% 议题被评价为「有用且下一步可执行」；列出无用原因。
- 所有已确认行动都有负责人和期限/观察计划；团队实际反馈率建议不低于 80%。用户不执行时记录原因，不能由系统代标完成。
- 老板比较前后资料整理与协调时间，建议中位数减少 30%；用实际记录验证，不能只用满意度代替。
- 预测仅评价当时已发布、后续实际成熟且范围一致的记录；与简单基线比较，公布有效窗口和误差。未优于基线时保留简单基线并限制用途。
- 经营收益按实际证据报告；没有可比较对照时只报告观察结果与偏差，不宣称 NEO 创造了全部增长。
- 若数据准备成本过高、建议无用或团队不跟进，调整流程与场景；完成代码不等于产品价值验收通过。

## 8. 行业扩展顺序与独立验收

| 行业 | 可复用基础 | 需要新增/完善 | 独立验收场景 |
|---|---|---|---|
| 消费品牌/电商 | 当前客户、SKU、库存、到货、费用、预测和补货求解 | 成交承接调查、联合选择、团队执行与复盘 | 旺季供给与投放、退款费用异常各完成一周期 |
| 酒店 | 已有预订、入住、房晚、服务容量和部分情景计算 | 入住日/房型操作界面、预订进度、取消与房晚释放、渠道净贡献、促销响应 | 下周房晚空缺→比较促销/渠道→保存选择→跟进入住与贡献 |
| 画廊/高客单 | 身份与通用阶段、议题与跟进基础 | 兴趣、沟通、报价、预约/保留、可售作品、跟进反馈；稀疏需求处理 | 一条询价→明确跟进→记录反馈与成交/未成交原因；不套高频销量模型 |
| 健康/生活服务 | 通用客户与容量建模可借鉴 | 预约、到店、时段/人员容量、会员权益、再次购买及闲时活动 | 首次体验→比较跟进/活动→记录预约、复访与净贡献 |
| 零售/连锁 | 商品仓库、库存与调拨 | 门店维度、客流身份/口径、活动、尺码、店间可比性与跟进 | 同活动门店差异→调查供给/承接→调货或培训→同范围观察 |

建议首先交付电商闭环，酒店作为第二个复用验证场景。画廊、服务和连锁依据真实客户来源选择下一项，不同时铺开。制造已有后端能力保留，但本宣传文档未将其列为主要场景，不插入本轮优先范围。

## 9. 迁移与交付约束

- 每阶段开始记录当前在制改动与回退点；不把现有未提交更新统一归入新方案贡献。
- 保留单一 `/demo` 产品入口和已确认的经营术语；接口/页面按业务切片迁移。
- 数据性质、可知时间、来源、企业范围、方案同基线及执行真实性不因提速而削弱。
- 优先用已有成员权限和站内提醒完成团队使用；真实生产访问、备份恢复和来源凭据管理另做部署验收。
- 外部消息、自动投放、采购与公开上线不包含在本方案的默认执行范围。
- 单阶段交付清单统一为：可用业务路径、数据/计算范围、改动与迁移、验证证据、实质缺口。未通过阶段门槛不扩大行业范围。

## 10. 下一轮应交付的具体结果

下一轮执行 S0 和 S1 的一个完整切片：**新资料形成可信经营上下文 → 保存供给议题 → 首页追查库存与到货依据 → 进入已有预测与方案 → 刷新后继续原议题。**

它必须修复当前观察到的预测承接断点、解释缺口和加载状态，保留已有方案/选择，并建立可复用议题对象。完成后，S2 才围绕这个议题替换调查与核验路径。整个方案以可持续推进的经营工作为验收单位。
