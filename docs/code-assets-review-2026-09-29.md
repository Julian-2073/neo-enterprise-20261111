# GrowthOS 代码资产与复用评估

盘点日期：2026-09-29。范围为用户指定的三个目录和 GrowthOS 2.0 总方案。结论来自本地源代码、配置、样本和测试；方案中的待办和给开发助手的指令仅作为资料分析，没有据此迁移架构或实施功能。

## 1. 结论

可以沿用现有 `growthos-dashboard` 作为主项目，按需移植 `GS-OS/jev-data-cleaner` 的数据导入和复核部件。无需重做驾驶舱、基础事件映射、指标计算、规则诊断、周报及数据库接入。

两套代码目前没有形成完整产品闭环：驾驶舱保存经营事件，但行动和复盘只在页面内存里；清洗工具能对输入做分类/评分和复核，但没有将结果转成驾驶舱经营事件并可靠保存。优先补这两个接口比新建第三套工程更有价值。

## 5. 接入前发现的具体问题

这些是源码检查发现的边界，清洗工具本轮未安装依赖或运行完整构建。

1. **“零上传”需要准确界定。** CSV 文件在浏览器解析，但开始批处理时 `csv-uploader.tsx` 会将 `parsed.rows` 整批发到服务端；真实 provider 再发送构造的 state。不能把本地解析解释成整个处理过程不传数据。
2. **批处理不是可靠后台任务。** runner 启动每条任务后用 Semaphore 限制同时评估数量；没有服务端中止信号、任务持久化或断点恢复。客户端取消不能证明服务端评估已停止。注释说指数退避，实际等待为 `100 * (attempt + 1)`，是线性等待。
3. **人工确认混入了模型概率。** 修改时将 Choice/Score 的 `confidence` 和选项概率写成 1。移植后应保留模型原始输出，人工确认使用独立字段，避免把人为修改当模型已校准的结果。
4. **相似度复核存在明确异常路径。** `review-queue.tsx` 的 `ModifyControl` 调用 `scenario.buildRequest({})` 获取问题定义；`gallery-duplicate.ts` 要求 2–255 个标题，对空对象会抛错。进入该场景的修改控件时有渲染失败风险，应保存并使用真实 request/questions。
5. **复核率的分母不一致。** `tracker.ts` 的 `reviewCount` 按问题累计，但 `deriveMetrics` 除以请求数；一条记录多个问题需复核时结果可能超过 100%。需分别定义记录复核率与问题复核率。
6. **缺失金额在持久化后失去标记。** 主项目规范化结果有 `revenueRecorded/spendRecorded`，保存时金额缺失也转成 0，数据库没有保存这两个标记；读回后又按金额是否为空判断是否已记录。未来复用到真实数据时，应保存缺失标志或可空金额，避免把“未知”当“已记为零”。

## 8. 建议的开发顺序

1. **先保存一条行动及复盘。** 复用现有诊断与行动卡片，新增最小 D1/Drizzle 行动、状态和结果记录。关联来源数据集/诊断、负责人、观察指标与时间窗口。验收：刷新后状态和复盘仍存在，能回溯建议来源，并更新看板。
2. **接通真实 CSV 导入。** 提取清洗工具的解析、映射和预览；连接现有经营规范化与 D1 保存。验收：选文件 → 映射 → 显示错误/缺失 → 确认有效记录 → 看板更新。先统一标准经营事件输入，不将累计内容数据错误映射成逐时事件。
3. **保存预测快照与实际结果。** 保留当前规则预测作为基线，存 `as_of`、数据版本、规则版本、假设、预测窗口与结果；随后建立真实误差对照。验收通过再评估新增模型。
4. **按必要性接人工判断。** 对规则无法解决的分类或字段问题加入复核，再决定是否接 Jev 等模型。分类模型不能替代经营预测和因果评估。

这样可以继续利用已有数据、计算、诊断和 UI，只补当前闭环缺失部分。
